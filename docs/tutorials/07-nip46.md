# 07 — Remote signers with NIP-46

**You build:** a login that works with no browser extension at all, against a key
that stays on the user's phone.

**You need:** tutorial 06 finished, or any working copy of `examples/merchant-app`.
A NIP-46 signer to test with — [nsec.app](https://nsec.app) in a second browser
tab is the least trouble.

> **On the transcripts.** Unlike the previous tutorials, the pairing flow here is
> **not** a captured run — it needs a live bunker on a live relay, which is not
> reproducible from a repository. Code and defaults are read from the
> implementation; the sequences are described, not pasted. Where a value is quoted
> it comes from the source, and the file is named.

---

## 1. The swap is three lines

This is the payoff for `SessionSigner` being an interface. Everything from
tutorial 02 onward — `login()`, `resume()`, `stepUp()`, the identity guard, the
locking — is written against it, and none of it knows or cares which kind it got.

```ts
import { createNip46Signer } from '@imani/nap-client-nip46';

const signer = createNip46Signer({ connectionToken: 'bunker://…' });
await signer.connect();
// From here on, identical to the extension signer.
```

Hand that to `createNapSession({ baseUrl, signer })` and the rest of the app is
unchanged. The server cannot tell the difference either — it sees a NIP-98 event,
and a signature is a signature.

`@imani/nap-client-nip46` is the ninth package and **the only one that talks to
relays**. Nothing else depends on it. An app that does not want WebSocket code in
its bundle simply does not install it, and loses nothing else.

> **What NAP is, and what NIP-46 is.** They are not competitors and it is worth
> being clear which does what before wiring either. RFC
> [Appendix A](../NAP-v2-RFC.md) is the comparison; Appendix B.3 has the sequence
> diagram for this exact combination. Neither is restated here.

## 2. Two directions, and who starts

There are two ways to establish a pairing, and choosing between them is a UX
decision, not a technical one.

**`bunker://` — the browser reaches out.** The user copies a URL out of their
signer and pastes it into your page. The URL carries the signer's pubkey, its
relays, and a secret. Best when the user has the signer in front of them on the
same device.

**`nostrconnect://` — the signer reaches in.** Your page generates a URI and
displays it; the user scans or pastes it into their signer, which then connects
back. Best on desktop with the key on a phone. Omit `connectionToken` and supply
`relays`, and the signer emits the URI through `onConnectionUri`.

`examples/merchant-app/src/web/RemoteSigner.tsx` offers both from one field —
blank means "scan me":

```tsx
const signer = createNip46Signer({
  ...(token.trim() ? { connectionToken: token.trim() } : {}),
  relays: ['wss://relay.nsec.app'],
  onAuthUrl: setAuthUrl,
  onConnectionUri: setUri,
  metadata: { name: 'Merchant app', url: window.location.origin },
});

await signer.connect();
```

The example renders the URI as selectable text rather than a QR code, because a QR
code needs a dependency and every mobile signer accepts a paste. Add one if your
users are scanning.

`metadata` is what the user sees in their signer's approval prompt. Fill it in —
"Merchant app wants to sign" is a decision the user can make; an unnamed client is
not.

### What the user actually does

1. Presses **Connect remote signer**.
2. Their signer shows an approval prompt naming your app and the permissions
   asked for.
3. They approve — and that is the last prompt of the pairing. NAP asks for
   exactly one permission, `sign_event:27235` (`DEFAULT_PERMISSIONS` in
   `connection.ts`): kind 27235 is NIP-98, and nothing else. A signer that
   pre-grants it will not ask again on subsequent logins.
4. Sometimes, step 2½: the signer answers with an `auth_url` instead — it wants
   the user to visit a page first, to unlock or to approve a new client. That is
   what `onAuthUrl` is for. It is neither an error nor a decline, and rendering
   it as one strands the user at the only step that would have unstranded them.

## 3. Decryption does not authenticate anybody

**Read this before you write your own pairing UI.** It is the trap this package
exists to have already fallen into.

When your page publishes a `nostrconnect://` URI, it is publishing its client
pubkey — into the URI itself, and into the `#p` filter that every relay serving
that subscription can see. The pubkey is public by construction. And NIP-44
conversation keys are ECDH, so **anybody** can encrypt something your page will
decrypt successfully.

So decryption proves nothing. The only thing that proves the sender read your URI
is the secret coming back:

```ts
if (result !== 'ack' && result !== connection.pointer.secret) {
  throw new Nip46Error('SECRET_MISMATCH', …);
}
```

The consequence that is easy to get wrong: an `{error}` payload arriving during
pairing is **not** a decline. It is unauthenticated, and treating it as a verdict
hands every relay operator — and every passive observer — a kill switch on every
pairing attempt in flight. They publish one encrypted `{error}`, your page closes
the subscription, and the real signer's answer arrives at nobody.

`connection.ts` records such a payload and lets the timeout decide, using it only
to classify the failure that was going to happen anyway:

```
declineReason ??= payload.error;
```

An attacker who wants to be a nuisance can change *which* error message a stalled
pairing reports. That is the entire remaining attack, and it is the right trade.

`SECRET_MISMATCH` is worth surfacing in its own words. It is not a wrong password
and it is not the user's fault — something on the relay answered a pairing it
could not read. The example says "Something answered without the pairing secret.
Start a new pairing."

## 4. Not re-pairing on every reload

Pairing is a two-device dance. Making the user redo it because they refreshed the
page is the fastest way to make remote signing feel worse than it is.

Pass a `SecretStore` and a passphrase:

```tsx
...(passphrase
  ? { secretStore: createWebCryptoSecretStore('merchant.nip46'), passphrase }
  : {}),
```

Then `connect()` covers both cases — it tries the stored pairing first and pairs
afresh only if there is nothing to restore. The UI does not have to know which
happened.

Three properties of that store worth knowing before you wire it:

- **What is stored is not the user's key.** It is this pairing's own client
  secret key, plus the bunker pubkey and relays — an AES-GCM ciphertext, PBKDF2
  over a passphrase the store never holds. The user's key was never in the page
  and is not in the store either.
- **Every unreadable record means the same thing: pair again.** Absent, wrong
  passphrase, or written by a version this build does not understand — all three
  return `null` rather than throwing. A forgotten passphrase must not be a dead
  application.
- **A stored pairing the signer has revoked is cleared, not retried.** If the
  restore fails because the bunker moved or dropped you, the record is deleted so
  the next visit pairs cleanly instead of failing identically forever.

There is still a passphrase prompt on reload, which is a real cost. Whether that
beats re-pairing is your call — for a merchant app it does; for a page a user
visits twice a year it may not.

## 5. Relays are slow, and that is not a bug

An extension signature is a function call. A NIP-46 signature is: encrypt, publish
to N relays, wait for the signer to notice, wait for it to answer, decrypt. The
defaults in `timeout.ts` are sized for that reality rather than for a fast day:

| | Default |
| --- | --- |
| `connectTimeoutMs` | 15 000 |
| `signTimeoutMs` | 30 000 |
| `pingTimeoutMs` | 5 000 |

Thirty seconds for a signature is not pessimism — the user may have to pick up
their phone, unlock it, and press approve.

What that means for your UI:

- **Every signing action needs a pending state**, and it needs to survive half a
  minute without looking broken. "Waiting for your signer…" beats a spinner.
- **Failures are network-shaped and have nothing to do with the user.** The
  taxonomy is six codes — `INVALID_TOKEN`, `UNREACHABLE`, `TIMEOUT`, `DECLINED`,
  `SECRET_MISMATCH`, `PROVIDER_ERROR` — and only `DECLINED` is a choice somebody
  made. `describeNip46()` in the example renders each as itself.
- **`ping()` returns `false` rather than throwing.** A dead bunker is an answer.
  Use it to show connection state instead of discovering it mid-signature.
- **The session lasts; the signer round trip does not repeat.** Once logged in,
  ordinary requests carry a cookie. The relay is on the login path and the
  step-up path only — which makes tutorial 05's refresh loop worth more here than
  anywhere else.

## 6. One copy of `nostr-tools`, and it must be recent

Two constraints, and they compound.

`BunkerSigner.fromBunker` and `fromURI` need `nostr-tools ^2.23.0`, so that floor
applies to the whole workspace once this package is installed.

And it must be **deduped**. Four packages depend on `nostr-tools`; if your app's
copy differs from NAP's, you get `verifyEvent` failures that look like malformed
signatures and are not. Check before you debug anything else:

```bash
npm ls nostr-tools
```

```
├─┬ @imani/nap-client-nip46@0.10.1
│ └── nostr-tools@2.23.3 deduped
├─┬ @imani/nap-client-web@0.10.1
│ └── nostr-tools@2.23.3 deduped
```

Every line saying `deduped` against the same version is what you want. A nested
copy at a different version is the bug.

## 7. Try it

1. Open [nsec.app](https://nsec.app) in another tab and create or unlock a key.
2. Run the merchant app (`npm start` and `npm run dev:web`), and use **Connect
   remote signer** with the field left blank.
3. Copy the `nostrconnect://` URI the page prints into nsec.app.
4. Approve. The page signs you in without ever asking for an extension.
5. Reload with no passphrase set: you pair again. Set one, sign in, reload: you
   do not.
6. Press **Update payout settings** from tutorial 06. The step-up prompt now
   arrives on your phone — and if the signer pre-granted `sign_event:27235`, it
   arrives nowhere at all. That is §5 of tutorial 06 in one keypress.
